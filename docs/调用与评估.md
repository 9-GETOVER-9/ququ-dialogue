# 调用与评估

以下是本项目建议的独立实现流程，不是已经部署的服务。

## 日常对话

```text
选择形象
 → 后端校验用户和会话归属
 → 加载固定版本角色提示词
 → 按顺序读取当前会话历史
 → system + 历史 user/assistant + 本轮 user
 → 调用自己的模型服务，流式显示正文
 → 保存完成的回答与提示词版本
```

先用一个文本角色、一个模型调用完成日常回答即可。不同外观不必对应多个 Agent。模型和凭证由自己的后端配置；这份资料不指定未核验的原产品型号或参数。

消息组织示意：

```text
system: prompts/v0.3/system.txt 全文
user: 上一轮用户输入
assistant: 本组模型自己的上一轮完整回答
user: 本轮用户输入
```

新会话使用空历史。中断的部分回答不能冒充已完成回答。重试应有幂等处理，避免重复生成与计费。若将长历史压缩成摘要，要分别保留用户事实、模型推测和被撤回的旧建议。

课程检索可作为后续独立功能：先检索正文，再给模型相关片段及课程来源。先测试提示词本身，再比较加入课程上下文后的效果，避免同时改变多个变量。当前没有实现检索后端，也未证明测试产品使用课程检索。

## 对照方法

固定自己可用的模型及参数，分别使用角色配置参考、v0.2 和 v0.3。各组独立新建会话，每一轮加入该组实际生成的历史。保留模型标识、参数、prompt 摘要、输入、输出和时间。

已公开的同题记录是开发材料，不作为独立泛化成绩。另用新的中文情境检查：

- 联系少但持续见面、说到做到时，是否仍机械判断不重视。
- 用户自己反复试探时，是否能指出其做法与目标冲突。
- 已经表达需要但持续被敷衍时，是否给出具体边界，而非只让用户再沟通。
- 补充足以改变判断的事实后，是否明确撤回旧建议。
- 仅要求一句回复时，是否只给话术且不虚构事实。
- 稳定关系中的感谢与分享，是否仍被强行解释为博弈。

多次生成用于观察输出波动。分别比较判断依据、建议具体度、语气、修正能力及格式服从，不以一个模糊的“相似度百分比”代替这些检查。用过的题目若参与修改提示词，就不再是独立测试题。

当前仅完成文档与提示词整理，尚无自建模型 A/B 结果。
